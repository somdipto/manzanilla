CONCLUSIONS:
1. The sentence-boundary split at a 600ms pause is universal on the hosted route: every ASR model
   (scribe_v2_realtime, transcribe-stream-1, nova-3) and every response_wait setting tested (300,
   900) split. The hosted agents config surface exposes NO endpointing/VAD knob (agents API asr =
   model/multilingual/strict_language/keyterms; conversation = response_wait/response_max_wait/
   eagerness/interruptible/interruption_sensitivity/echo_guard/speculative_response). turn_detection
   knobs exist only in the streaming STT websocket API, not the hosted agents API.
2. response_wait_ms does not affect user-turn text assembly (900ms still split). Production's 300ms
   wait is already the minimum and does not cause the split; raising it adds reply latency for nothing.
3. Meaning loss happens only when the ASR also mangles the first word after the pause ("saying" ->
   "And" or "Dang", 3/6 hard-cut runs). When the word survives, gemini-3.8-flash stitches the split
   fragments into the correct meaning on its own (5/5 "Saying" runs, hint or not).
4. Prompt hardening (explicit fragment-rejoin instruction) does not recover a mangled word
   ("Dang" -> "Rayos" literal translation). Not an effective fix.
5. nova-3 is strictly worse for this case (fragments into separate turns, worse mangling). Production's
   scribe choice for broad pairs stands. transcribe-stream-1 shows no advantage on the hosted route.
6. The word mangling appears tied to the synthetic HARD-CUT digital-silence pause: with a room-tone
   pause (low-level noise), 2/2 runs transcribed "Saying" correctly. The synthetic test likely
   overstates the real-world failure rate; the real rate on device mics is unknown but non-zero
   (the user's original event happened on a real phone).
7. No premature/wrong-partial audio observed in any run: every assistant reply arrived after the
   complete utterance. This does not universally rule out premature draft voicing, only none observed
   in 9 hosted runs.
