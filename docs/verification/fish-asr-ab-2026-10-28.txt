LATENCY RECONCILIATION (first run reported median 1530ms; A/B runs report ~700ms):
  The 1530ms was a PROBE PROTOCOL ARTIFACT, not real latency. The first probe sent 1.5s of
  silence frames BEFORE it started reading events, so the commit (which actually arrived during
  the silence window) sat in the queue and was timestamped when read. The A/B probe timestamps
  events at arrival via a concurrent collector. Corrected committed latency for plain short
  sentences: ~540-780ms end-of-audio -> committed, stable across 3 auto sessions (medians
  776, 698, 701) and 2 vad900 sessions (734, 746). No improvement claim: same provider, same
  route, only the measurement protocol changed.

MODE SEMANTICS (Fish docs, llms-full.txt):
  auto: semantic turn judgement; "a short pause mid-sentence usually does not end the turn";
        silence_timeout_ms (default 5000, min 3000) is only a safety net. eager only in auto.
  vad:  turn ends after silence_timeout_ms of silence (default 700, allowed 300-60000);
        every turn is a user turn; no eager events.
  A session must START in vad for clean vad semantics; a mid-session switch from auto keeps
  auto's judgement artifacts (first vad500 run used a mid-session switch and produced
  user_turn=false, contradicting vad semantics - discarded as protocol-invalid).

NEGATION-PAUSE CASE ("I am not" + 600ms silence + "saying the room is dirty."):
  auto run 1: SPLIT into 2 committed turns ("I am not." / "The room is dirty."), both
              user_turn=true. A route that generates per committed turn answers the wrong
              (negation-less) statement.
  auto run 2, 3: single turn, all words present. Split rate observed: 1/3 auto sessions.
  ALL auto runs: eager_end_of_turn fired DURING the 600ms pause (end_to_eager -1.4 to -1.7s),
              i.e. eager consistently treats the pause as turn end even when the final commit
              does not split. Any route that starts generation on eager (the self-hosted worker
              does) will generate from the wrong partial on paused negations, deterministically.
  vad900 (clean start, silence_timeout 900ms): 2/2 sessions single turn, all words present,
              committed 676-680ms on this case. No split, as expected (600 < 900).

OTHER CASES:
  pause-700ms "Could I ... get a late checkout on Sunday?": no split in any mode/run
    (splitting is content/prosody dependent, not a pure threshold). Provider inserts a
    "[pause]"/"..." marker at the gap; word content complete.
  double-negation-400ms: no split, both negations preserved, every run.
  long-utterance (~8s): full correct transcript in all modes once the input PCM was complete.
    TRUNCATION CORRECTION: the earlier "...without any pr" truncation was TWO probe artifacts,
    neither provider-side: (1) the first 8.pcm was TTS-truncated mid-word, fixed by synthesizing
    in two calls; (2) my results field sliced transcripts at 120 chars. With complete audio and
    full supplied-text comparison, transcript_matches_input=true (verified in 2 sessions).
    TTS-truncation proof chain: original single-call synthesis returned 7.75s of audio ending
    mid-word (speech energy in the final window) and ASR faithfully committed "...pr"; a repeat
    single-call synthesis of the same text returned 8.45s ending in silence (complete); the
    two-call PCM committed the complete supplied text. So the TTS cut was a non-deterministic
    synthesis-side truncation; no provider truncation observed anywhere.

ENDPOINT-LATENCY TRADEOFF (medians, end-of-audio -> committed):
  auto:   776 / 698 / 701 ms (3 sessions; eager at 272-351ms when it fires after end)
  vad900: 734 / 746 ms (2 sessions; no eager events in vad mode)
  On these cases vad900 did NOT add committed latency vs auto, because auto's semantic judge
  also waited ~700ms after speech end here. vad mode removes eager, so a route that relies on
  eager for early LLM start loses that head start (auto eager fired 272-351ms after end on
  plain sentences, i.e. ~400ms before commit).

CANDIDATE MITIGATIONS (tested here, provider-side only; merits/gaps):
  1. vad mode with silence_timeout ~900ms: held paused negations together 2/2, no measured
     committed-latency cost on these cases, deterministic threshold behavior. Gaps: loses
     eager head start and auto's user_turn/backchannel classification (vad commits every turn
     as user_turn, including non-speech sounds - main's interruption/overlap concerns would
     need app-side filtering); threshold above a real end-of-turn pause adds up to
     (threshold - natural pause) latency on genuinely finished turns; n=2.
  2. ROUTE SEMANTICS CHECK (code read, 2026-10-28): the self-hosted worker REQUESTS eager in
     its ASR config but never consumes eager_end_of_turn events - generation starts only on
     committed turns with user_turn=true (session.py:204-214), and interruption starts only on
     user_turn_taken (session.py:200-202), which cancels generation and flushes queued audio
     (already-played audio is not retracted). So on the worker route: eager-at-pause is inert;
     the wrong-partial path is the 1/3 split-commit case, where turn 1 ("I am not.") generates
     and may briefly play before turn 2's user_turn_taken cancels it.
     The app's hosted route sets speculative_response=true (FishPlan.kt:160): Fish's server
     drafts a reply during response_wait_ms=300 (max 600ms) and discards the draft if speech
     continues. The app consumes no eager events client-side (no eager handling in
     HotelGateway.kt or FishSessionAdmission.kt). A 600ms mid-sentence pause lands exactly at
     the 600ms max-wait boundary: whether the drafted wrong reply becomes audible depends on
     which side of the boundary the resumed speech arrives - undetermined from code/docs,
     needs a hosted-route live test.
  3. App/worker-side turn-stitching window after commit: NOT implemented/tested here. Would
     cover the residual auto split but adds a wait on every turn end (full-duplex harm main
     warned about) unless made conditional; no measured design yet.
